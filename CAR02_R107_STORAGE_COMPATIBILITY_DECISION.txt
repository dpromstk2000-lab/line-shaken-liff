What is documented:
- Supabase storage.from(bucket).remove([path]) deletes objects by path, and Storage API must handle object deletions (SQL metadata deletion is not a substitute).
- Standard upload can use upsert:true / x-upsert to replace objects at an existing path; default non-upsert fails when the path exists. Concurrent upsert writes can replace existing object content.
- Storage authorization depends on permissions/policies. A high-privilege server credential can invalidate assumptions made for less-privileged users.
- The documentation checked does NOT establish that the CAR02 deployment supports an atomic (path, version, SHA256) conditional deletion operation. Absence of evidence is NOT evidence that no platform API exists.

R106's deleteIfMatch is an in-process mock. It is NOT proven interoperable with production Supabase Storage. A HEAD/read followed by remove(path) is NOT atomic: a replacement between calls can be deleted incorrectly.

R107 immutable-path candidate:
1) Backend assigns a new unpredictable object identifier; tenant/order/report scope is server validated.
2) Every write uses create-only semantics; no upsert/update or alternate writer may overwrite those paths.
3) A durable unique path reservation and never-reuse tombstone must survive retry, crash and recovery across all deployments; the R107 in-memory model is NOT sufficient.
4) Delete authorization is limited to one audited component and correct tenant; private bucket plus policy review.
5) Real staging environment must verify unauthorized overwrite attempts, concurrent writes, delete/retry, lost acknowledgments and object existence independent of metadata.
6) If any writer can replace a key or real delete semantics cannot be proven, DO NOT call standard remove(path) as a version-bound delete. Keep it blocked pending reviewed provider-specific alternative.
